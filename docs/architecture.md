# Архитектура проекта

Этот документ объясняет простыми словами, как устроен проект Sentinel и как его части работают вместе.

## Главная идея

Проект разделён на слои.

Слой — это часть приложения со своей задачей. Один слой отвечает за экран, другой — за данные, третий — за документацию.

Такой подход нужен, чтобы код не смешивался в одну кучу. Интерфейс занимается интерфейсом, логика мониторинга занимается метриками, а документация объясняет проект человеку.

## Какие слои есть в проекте

В текущей структуре проекта основные части такие:

- `SystemMonitor.App`
- `SystemMonitor.Core`
- `docs`

`SystemMonitor.App` — это внешний слой приложения. Его видит пользователь.

`SystemMonitor.Core` — это внутренний слой с основной логикой мониторинга.

`docs` — это документация проекта.

## SystemMonitor.App

`SystemMonitor.App` отвечает за внешний вид приложения.

Здесь находятся окно, экраны, стили и ViewModel.

Простыми словами, этот слой отвечает на вопрос: что пользователь видит на экране?

В этом слое есть:

- `Program.cs` — запускает приложение.
- `App.axaml` — подключает общие стили и ресурсы.
- `App.axaml.cs` — создаёт главное окно.
- `Views` — описывают экраны через XAML.
- `ViewModels` — подготавливают данные для экранов.
- `Styles` — задают цвета, кнопки, карточки и общий внешний вид.

Важно: `App` не должен сам заниматься низкоуровневым чтением данных из Windows. Если интерфейс сам начнёт читать CPU, RAM и процессы, архитектура станет слабее. Экран должен показывать данные, а не добывать их напрямую.

## SystemMonitor.Core

`SystemMonitor.Core` отвечает за основную логику мониторинга.

Простыми словами, этот слой отвечает на вопрос: какие данные о системе нужны приложению и как их получить?

В этом слое есть несколько важных частей.

### Models

Модели описывают данные.

Например:

- `CpuSnapshot` хранит снимок загрузки процессора.
- `RamSnapshot` хранит данные об оперативной памяти.
- `ProcessEntry` хранит информацию об одном процессе.

Модель не должна управлять интерфейсом. Её задача — хранить понятную структуру данных.

### Interface

Интерфейсы описывают контракты.

Контракт говорит: какой метод должен быть у сервиса и какой результат он должен вернуть.

Например:

- `ICpuMetricsService` описывает сервис CPU.
- `IMemoryMetricsService` описывает сервис RAM.
- `IProcessMetricsService` описывает сервис процессов.

Интерфейс не объясняет, как именно внутри читаются данные. Он только фиксирует, что сервис обязан уметь делать.

### Services

Сервисы получают реальные данные из системы.

Например:

- `CpuMetricsService` получает данные о процессоре.
- `MemoryMetricsService` получает данные об оперативной памяти.
- `ProcessMetricsService` получает список процессов и их показатели.

Сервис — это рабочая часть слоя `Core`. Он не рисует кнопки и окна. Он занимается своей задачей: получает метрики и возвращает их в виде моделей.

### Collectors

`MetricsCollector` собирает данные из разных сервисов.

Его можно представить как координатора.

Он обращается к сервису CPU, сервису RAM и сервису процессов, а потом отдаёт наружу готовый набор данных.

## Как данные проходят через приложение

Общий путь данных выглядит так:

1. Windows хранит реальные данные о процессоре, памяти и процессах.
2. Сервисы из `SystemMonitor.Core` читают эти данные.
3. Сервисы создают модели: `CpuSnapshot`, `RamSnapshot`, `ProcessEntry`.
4. `MetricsCollector` собирает данные из сервисов.
5. `SystemMonitor.App` получает подготовленные данные.
6. ViewModel в `App` подготавливает их для экрана.
7. XAML-экран показывает данные пользователю.

В коротком виде:

```text
Windows -> Core Services -> Core Models -> MetricsCollector -> App ViewModels -> XAML Views -> User
```

## Как App и Core работают вместе

`App` и `Core` не должны делать одну и ту же работу.

`Core` отвечает за смысл данных.

`App` отвечает за показ данных.

Например, если нужно показать загрузку процессора:

1. `CpuMetricsService` получает загрузку CPU.
2. Он возвращает `CpuSnapshot`.
3. ViewModel получает это значение.
4. XAML показывает процент на экране.

Если позже поменяется способ получения CPU, менять нужно `Core`.

Если позже поменяется внешний вид карточки CPU, менять нужно `App`.

Это и есть смысл разделения на слои.

## Почему это лучше, чем всё в одном месте

Если весь код написать в одном окне, проект быстро станет неудобным.

Интерфейс будет одновременно рисовать экран, читать Windows API, считать данные и хранить состояние. Такой код сложно объяснять, проверять и менять.

Разделение на слои решает эту проблему:

- интерфейс можно менять отдельно от логики мониторинга;
- сервисы можно проверять отдельно от окна;
- модели данных проще понимать;
- проект легче защищать на презентации;
- новые экраны можно добавлять без переписывания всего приложения.

## Важный момент про Infrastructure

В некоторых проектах есть отдельный слой `Infrastructure`.

Обычно туда выносят работу с внешним миром: Windows API, файлы, базу данных, сеть или сторонние библиотеки.

В текущей структуре проекта отдельной папки `SystemMonitor.Infrastructure` нет. Поэтому сейчас работа с системными метриками находится в `SystemMonitor.Core/Services`.

Это не ошибка для учебного проекта. Но если проект будет расти, часть кода из `Services` можно будет вынести в отдельный инфраструктурный слой.

Тогда структура стала бы такой:

```text
App -> Core -> Infrastructure -> Windows
```

Но сейчас фактическая структура проще:

```text
App -> Core -> Windows
```

## Простое итоговое объяснение

`SystemMonitor.App` — это лицо приложения.

`SystemMonitor.Core` — это мозг приложения.

`Models` хранят данные.

`Interfaces` задают правила для сервисов.

`Services` получают реальные метрики.

`MetricsCollector` собирает всё вместе.

ViewModel берёт готовые данные и отдаёт их экрану.

XAML показывает эти данные пользователю.
